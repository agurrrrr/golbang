## (a) 회귀 — golbang P1 순차 대기 vs P2 스케줄러

같은 release 바이너리. P1 = `--n-parallel 1 --queue-size 4` (후발은 선발 종료까지 슬롯 대기).
P2 = `--n-parallel 2 --queue-size 2` (후발은 다음 `llama_decode` 반환 직후 join).

| 지표 | P1 순차 대기 (`np=1`) | P2 스케줄러 (`np=2`) |
|------|----------------------|----------------------|
| 선발 TTFT | 23.2 ms | 23.3 ms |
| **후발 TTFT** | **132.5 ms** | **50.1 ms** |
| ITL (요청 평균) | 5.5 ms | 9.4 ms |
| 요청당 tok/s (평균) | 194.3 | 114.5 |
| 총 wall (늦은 쪽) | 210.2 ms | 180.4 ms |
| VRAM used | 32139 MiB (+844) | 32167 MiB (+872) |

후발 TTFT는 P1 대비 낮음 (132.5 → 50.1 ms). 처리량 승리는 조건이 아님. 통합 batch라 ITL/요청당 tok/s는 나란히 도는 쪽이 높다.

인프로세스 debug 테스트(`two_slots_both_complete_and_late_ttft_beats_serial`, `max_tokens=8`)도 같은 방향: 후발 TTFT serial 119.8 ms vs parallel 30.5 ms.

## (b) 경쟁 — llama-server 동일 조건 기록

> 처리량 우위는 필수 조건이 아니다. 동률 + 제어면 개선이면 통과.

llama-server 2회(워밍 후 2번째가 안정). Qwen3 `--jinja` 스트림은 `delta.reasoning_content`로 토큰이 나와 TTFT/ITL은 그 필드를 포함해 쟀다.

| 지표 | golbang P2 | llama-server (warm) |
|------|-----------|---------------------|
| 후발 TTFT | 50.1 ms | 49.8 ms |
| 선발 TTFT | 23.3 ms | 49.3 ms |
| ITL | 9.4 ms | 6.1 ms |
| tok/s (요청 평균) | 114.5 | 178.0 |
| VRAM used | 32167 MiB (+872) | 31982 MiB (+687) |

TTFT는 동률에 가깝다. tok/s는 llama-server가 높다. P2 성공 조건이 아니므로 그대로 적는다.

## 제어면 관찰 (정성)

- 정책 교체: `SchedulePolicy` trait (`join` / `evict` / `rank`). 기본 `FifoPolicy`. `--policy fifo`. 유닛 테스트가 object-safe 교체를 확인.
- decode 중 즉시 503: bounded `try_send`. `n_parallel=1, queue=1`에 동시 4요청 → 최소 1건 HTTP 503 + `Retry-After: 1`. 테스트 `decode_busy_returns_503_immediately`.
- 취소: HTTP/핸들러는 즉시 `CancellationToken` 취소. 슬롯 회수는 다음 decode 경계. 테스트 `cancel_is_accepted_immediately_and_reclaimed_after_decode`.
- join 타이밍: 로그 `join after decode boundary`. 동시 2요청 예: `iter=4 slot=0` 다음 `iter=5 slot=1`.
